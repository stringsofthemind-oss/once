LIVE FAILURE-MODE DEMO

The write succeeded. The acknowledgement disappeared. What should the agent do next?

This is the dangerous retry boundary: the caller sees a timeout, but the provider may already have committed the external effect.

Core rule: a timeout is not proof of failure. If the first attempt may have committed, blindly sending the write again can duplicate the real-world action.

This browser demo is an explanatory simulation of the failure mode. Repository hostile-retry tests provide the executable evidence for tested Once paths.

What the simulation represents

Both lanes begin with the same logical operation. The provider commits the first write, but the response is lost. The naive lane treats the timeout as failure and creates a fresh retry. The Once lane keeps the same logical operation identity, sees that execution truth is unresolved, and requires replay/reconciliation or blocks instead of guessing.

The decision model

CONFIRMED → replay or suppress. ABSENT → a protected execution may proceed. UNKNOWN → block or reconcile. CONFLICT → the same logical identity was reused with different effect-bearing data, so block.

Claim boundary: Once does not claim universal exactly-once execution. Safe behavior depends on stable logical identity, effect binding, durable state, controlled execution boundaries, and sufficiently authoritative reconciliation when needed.
