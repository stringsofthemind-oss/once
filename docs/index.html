IETF / RFC 9110 / §9.2.2

RETRY ≠ SAFE

HTTP distinguishes idempotent operations because a communication failure can leave the client needing to retry without knowing whether the first request already took effect.

RFC 9110 says a client should not automatically retry a non-idempotent request unless it can know the retry is safe or determine that the original request was never applied.

THE ONCE DECISION MODEL

The retry gets a decision.
Not another blind execution.

Once does not treat a missing response as proof that nothing happened. It carries the same logical operation identity across retries, checks durable state and provider truth on supported paths, then chooses one of three outcomes.

CONFIRMED REPLAY / SUPPRESS
Reality already changed. Return the durable result or suppress the duplicate instead of executing the consequential action again.
ABSENT EXECUTE
No prior effect is established. When durable state and supported reconciliation establish absence, the operation may proceed.
UNKNOWN BLOCK + RECONCILE
Truth cannot be established yet. Fail closed rather than guess. Reconcile provider truth before another consequential execution is allowed.
CORE RULE SAME OPERATION ID
A timeout is not a result. Retries reuse one stable logical identity so Once can reason about the operation rather than treating every attempt as new work.

Scope: Once does not infer provider truth from a lost response. Safe recovery on supported paths depends on durable operation identity, durable state and authoritative reconciliation or equivalent downstream guarantees.

WHERE ONCE SITS

MCP helps the agent choose the protection.
The runtime enforces the decision.

Once separates agent-facing discovery and setup from the execution-safety boundary. The MCP server helps an agent assess a project, plan protection, apply supported setup and verify the connection. The runtime is what executes, replays or blocks a protected consequential operation.

MCP / AGENT LAYER ASSESS + CONFIGURE
Discovery, planning and verification. Agents can inspect the project, explain retry risk, plan setup, apply supported protection and verify Once is connected.
RUNTIME LAYER EXECUTE + REPLAY + BLOCK
The execution-safety boundary. Protected operations use stable identity, durable state and supported reconciliation to decide whether to execute, replay or fail closed.
DATA PATH APPLICATION -> ONCE -> PROVIDER
Protection sits on the consequential path. The runtime must be on the path of the side effect being protected. Installing the MCP server alone does not automatically guard every tool call.
BOUNDARY NO MAGIC INTERCEPTION
Explicit integration, explicit guarantees. Once protects supported operations that are wired through its execution boundary; it does not claim to intercept arbitrary external actions automatically.

In short: MCP makes Once legible and usable to agents. The runtime is the safety boundary that protects the consequential operation.

CURRENT TRUST BOUNDARY

Know what Once sees.
Know how failure behaves.

The current hosted SDK path is intentionally explicit about its boundary. Protected execution is authenticated to the Once service, operation data crosses that boundary, and the SDK fails with an error rather than silently bypassing Once when the service cannot be reached.

HOSTED EXECUTION PATH AUTHENTICATED
The SDK talks to the Once service. On the hosted execute path, the operation ID, provider alias and action payload are sent to the configured Once API using the Once API key.
PROVIDER REGISTRATION EXPLICIT SETUP
Provider access is configured, not inferred. For the current hosted HTTP provider setup, the provider base URL and provider token are registered with Once so the runtime can execute and reconcile supported protected operations.
ONCE UNREACHABLE ERROR / NO SILENT BYPASS
Protection does not disappear quietly. The SDK performs bounded network retries. If Once still cannot be reached, it raises a timeout or network error instead of silently sending the protected action directly to the provider.
REFERENCE EVIDENCE LOCAL SQLITE LABS
The crash labs are reference implementations. LangGraph and CrewAI evidence uses the SQLite reference backend and simulated provider ledgers. That proof is deliberately scoped separately from the hosted Once service.

Scope: this describes the current hosted SDK execution path and the published reference labs. It is not a claim about undocumented storage location, retention, encryption, compliance or deployment guarantees. Those should be documented separately before they are promised.

WHY ONCE

Keep provider idempotency.
Add recovery when the caller no longer knows.

Once is not a replacement for provider-native idempotency, database constraints or durable workflows. Those controls remain valuable. Once focuses on the retry boundary around a consequential external operation: one stable logical identity, durable execution state and a safe decision after an ambiguous outcome.

PROVIDER IDEMPOTENCY KEEP IT
Deduplicate at the provider boundary. When a provider supports an idempotency key or equivalent control, use it. Once complements that downstream protection rather than asking you to remove it.
ONCE IDENTITY + STATE + RECONCILIATION
Reason about the logical operation across attempts. Once carries stable operation identity across retries, records durable state and uses supported reconciliation to choose execute, replay or block instead of treating a lost response as a fresh action.
DATABASE / OUTBOX DIFFERENT BOUNDARY
Protect local state and message handoff. Unique constraints, transactions and outbox patterns can protect application or messaging boundaries. They do not by themselves establish whether an external provider already performed an operation after the response was lost.
DURABLE WORKFLOW STILL NEEDS SAFE EFFECTS
Durable orchestration and safe side effects solve different layers. A workflow engine can persist and retry a step. The external side effect still needs stable identity, downstream idempotency or reconciliation when execution crosses a failure boundary.

Rule of thumb: keep every useful downstream guarantee. Add Once when the same consequential operation may be retried, the first outcome can be ambiguous, and blindly executing it again would be unsafe or costly.

CURRENT SUPPORT

Know what is proven today.
Know what still requires manual integration.

Once deliberately separates detection from protection. The scanner can identify a wider set of consequential operations than the current Runtime HTTP execution contract protects automatically. Unsupported shapes fail closed or require an adapter instead of being presented as covered.

RUNTIME HTTP V0.1 PROVEN PROTECTED SHAPE
POST + application/json + stable identity. The current proven Runtime HTTP path protects an explicitly configured target, requires a non-empty valid JSON body and supports stable identity through an idempotency key or an application resolver.
HTTP RESPONSE REPLAY REQUIRED ON RUNTIME SETUP
Confirmed retries return durable application-visible results. Runtime HTTP setup pins the exact target URL and requires durable sanitized response replay for the registered provider version before the protected operation can use the confirmed replay path.
OTHER WRITE SHAPES ADAPTER / MANUAL REVIEW
Classification is broader than automatic execution support. PUT, PATCH and DELETE may be recognized as consequential, but Runtime HTTP v0.1 does not claim a proven protected execution contract for those methods. Unsupported request shapes are rejected rather than silently treated as protected.
SCAN + AUTO-APPLY CONSERVATIVE
Finding a candidate is not the same as protecting it. The scanner runs locally and can surface likely side effects. Automatic application is intentionally narrow: only a fully revalidated eligible callsite is patched; ambiguous or unsupported cases stay manual.

Current boundary: Once does not claim that every provider, HTTP method, request shape or detected side effect is automatically protected. Provider-specific guarantees and automatic transformation support should be evaluated separately from detection.
