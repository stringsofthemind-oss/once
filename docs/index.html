Retry safety for agent tools and applications

The same action should only happen once.

A payment, booking or ticket can succeed even when the response is lost. Once helps supported integrations reuse confirmed results and block uncertain retries instead of blindly repeating the action.

What Once changes

Your caller can retry.
The write needs a safe decision.

A retry library schedules another attempt. Once controls whether a protected consequential action is dispatched, replayed or blocked.

CONFIRMED

Reuse the original result.

The same logical identity and input can return a durably confirmed result without another protected dispatch.

CONFLICT

Stop changed input.

A changed amount, recipient or title under the same identity is rejected instead of silently becoming a different action.

UNKNOWN

Keep uncertainty safe.

If the outcome cannot be established, another dispatch stays blocked. Provider-specific truth can confirm the original result.

Safety boundaries

Simple to use. Explicit about what is protected.

Identity is your intent.

Keep one identity across retries. Use a different identity for a genuinely new action and bind every effect-bearing field.

Durability has a scope.

Local protection needs a persistent shared SQLite file on one machine. Separate hosts, ephemeral storage and network filesystems are outside that boundary.

Unknown can block progress.

Local mode does not redispatch an ambiguous write even after an absence observation. Recovery needs a supported provider contract; confirmed truth can be reconciled.

Keep provider-native idempotency. Route every consequential call through the protected boundary. Installing MCP or finding a candidate does not activate protection. Once does not promise universal exactly-once execution.

Questions before you integrate?

Why not just use an idempotency key?

Keep provider-native idempotency wherever available. Once adds a caller-side logical action boundary, durable result handling and explicit uncertainty decisions. Recovery still depends on the integration and downstream guarantees.

Why not store the result in my database?

A stored result helps replay known success. The hard case is the gap between the external effect committing and the result reaching your database. A local database transaction cannot atomically cover an arbitrary external provider. Once preserves that uncertainty instead of guessing.

What happens after a process restart or a Once crash?

Local protection recognises confirmed actions if every cooperating caller uses the same durable SQLite file on one machine. An interrupted claim can report IN_FLIGHT until its lease expires, then UNKNOWN; it is not blindly redispatched. Separate hosts and network filesystems are outside this local boundary.

What if the provider succeeded but the response was lost?

Once can leave the action UNKNOWN and block another dispatch. An authoritative, read-only provider lookup can confirm the original result where supported. If truth is unavailable, progress can stay blocked. In conservative local mode, reporting absence does not automatically permit redispatch after ambiguity.

What if the amount, recipient or other input changes?

Bind every effect-bearing field to the logical identity. Reusing that identity with a different supported payload raises CONFLICT rather than silently replaying an old result or sending a changed write.

Can Once suppress a genuinely new action?

Yes, if your identity collapses two different intentions into one. Use a stable ID for the same intentional action across retries, and a distinct ID for each genuinely new action. Scope it by tenant and action type. Do not mint a new ID merely to bypass UNKNOWN.

Where is state stored, and is an API key required?

Local TypeScript protection uses a durable same-machine SQLite file and needs no Once API key. Hosted execution sends the operation ID, provider alias and action payload to the Once service and requires authentication and provider setup. Choose the path explicitly.

Does Once add latency?

Local paths add state access; reconciliation adds a provider lookup when needed. Hosted paths also add network work. There is no universal latency promise. Measure the actual deployed integration; documented lab measurements are not production SLAs.

Can it automatically protect any function?

Automatic discovery and classification have explicit boundaries. Stable business identity and complete effect semantics still need trustworthy bindings. Unsupported call shapes fail closed or need reviewed integration.

What does ADAPTER_REQUIRED mean?

The detected operation needs provider-specific integration beyond the automatic transformer. Use the documented local-function or connected-tool route when suitable, or implement and validate an authoritative provider adapter. Detection alone is not protection.

Does installing MCP protect all my tools?

No. The MCP/plugin helps assess and configure a project. The runtime must be wired into the consequential call path. Exposing the original unprotected tool alongside its wrapper bypasses that boundary.

What happens if the hosted Once service is unreachable?

The SDK uses bounded retries, then raises a network or timeout error instead of silently dispatching the protected write directly. Do not handle that error by bypassing Once.
