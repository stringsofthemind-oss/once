PROVIDER RECIPE / STRIPE

A refund timeout should not become a second refund.

Use one stable logical operation identity across Once and Stripe's idempotency boundary, then reconcile provider truth instead of creating a fresh retry identity.

Pattern: derive one logical identity such as refund:order_123, bind the refund amount/payment target to it, and reuse the corresponding Stripe idempotency key for retries of that same intended refund.

Why Stripe is a useful example

Stripe documents idempotency keys for POST requests so clients can retry a request without accidentally creating a second operation. Stripe also exposes refund retrieval and listing APIs, which can provide provider-side evidence for reconciliation.

Illustrative flow

logical_operation = "refund:order_123"
effect = { payment_intent: "pi_...", amount: 2500 }

1. Once binds logical_operation + effect
2. Stripe POST refund uses an idempotency key derived for that logical operation
3. If the acknowledgement is lost, keep the Once state UNKNOWN
4. Reuse the same Stripe idempotency key for the same logical action
5. Where provider readback is needed, retrieve/list the relevant refund evidence
6. CONFIRMED -> replay/suppress
   ABSENT -> execute only when absence is authoritative
   UNKNOWN -> block/reconcile, do not invent a new refund identity
   CONFLICT -> block changed effect data under the same logical identity

Do not do this

// dangerous after an ambiguous timeout
await createRefund({ payment_intent, amount }, {
  idempotencyKey: randomUUID() // fresh key for the retry
})

A fresh per-attempt key can turn a retry into a new provider operation. Attempt identity and logical operation identity are not the same thing.

What Stripe itself provides

Stripe's API documentation says POST requests accept idempotency keys and that later requests with the same key return the first saved result once endpoint execution has begun. Stripe also supports retrieving a refund by refund ID and listing refunds, including filtering by charge or PaymentIntent.

What Once adds

Once is concerned with the application/agent-side logical operation: stable identity across retries, effect binding, durable execution state, routing, conflict detection, and a fail-closed UNKNOWN state. Provider-native idempotency remains valuable and should be used when available.

Claim boundary: this page is an integration recipe, not a claim that Once currently ships a production Stripe adapter or that Stripe plus Once creates universal exactly-once execution. Real integrations must preserve provider IDs, keys, request parameters, account scope, and reconciliation evidence appropriate to the deployed Stripe API version.
